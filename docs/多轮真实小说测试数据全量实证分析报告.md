## 一、数据存储位置与底层物理索引

本项目采用 **SQLite 关系索引 + 磁盘文件系统 (Hybrid Storage)** 架构，所有测试运行产生的过程数据与最终产物均持久化存储于以下位置：

### 1.1 SQLite 数据库表结构与索引位置
- **数据库文件绝对路径**：`D:\Project\novel2glagame\data\config\app.db`
- **核心数据表与记录职责**：
  1. `projects`：存储项目 ID、书名、章节总数、完成章节数（`ready_chapters`）、失败章节数（`failed_chapters`）、项目生命周期状态；
  2. `chapters`：存储章节 ID、章节序号、所属项目 ID、标题、场景数量、处理状态标志（`parsing_done`, `attribution_done`, `segmentation_done`）及错误信息（`error_message`）；
  3. `scenes`：存储场景 ID、场景序号、所属章节 ID、文本单元数、保真度审核通过标志（`fidelity_passed`）；
  4. `tasks`：记录每一个子任务的唯一 ID、任务类型（8 类）、重试次数、耗时及状态；
  5. `pipeline_runs`：记录 LangGraph 状态图的检查点（Checkpoint）与状态快照。

### 1.2 文件系统存储拓扑与落盘文件清单
- **磁盘存储根目录**：`D:\Project\novel2glagame\data\projects\`
- **单项目物理目录拓扑结构**：
  ```text
  D:\Project\novel2glagame\data\projects\{projectId}\
  ├── source.txt                                   # 原始小说全文
  ├── manifest.json                                # 项目清单与配置
  ├── chapters\                                    # 章节过程数据
  │   └── {chapterId}\
  │       ├── source.txt                           # 章节原始文本
  │       ├── narrative.json                       # 叙事单元分类结果
  │       ├── attribution.json                     # 说话人归属结果
  │       └── segmentation.json                    # 场景切分结果
  ├── scenes\                                      # 场景级核心产物
  │   └── {sceneId}\
  │       ├── vn_script.json                       # VN Script IR v1.0 步骤DSL
  │       ├── visual_prompt.json                   # 角色与背景提示词包
  │       └── fidelity_report.json                 # 保真度审查报告
  ├── assets\images\                               # 生成/占位美术资产
  │   ├── characters\                              # 角色立绘 (.png / .svg)
  │   └── backgrounds\                             # 场景背景 (.png / .svg)
  ├── export\{project_title}\                      # 导出的 Ren'Py 8.x 游戏工程
  │   ├── game\
  │   │   ├── script.rpy                           # 主剧情脚本
  │   │   ├── screens.rpy / gui.rpy / options.rpy  # Ren'Py 标准引擎配置
  │   │   └── images\                              # 游戏打包内嵌资源
  └── rag\                                         # 本地向量数据库存储
  ```

### 5.1 步骤类型 (Step Type) 统计分布

```
[R2 步骤分布占比]
```

- **立绘登场率**：平均每 8.2 个剧本步骤出现一次 `show` 指令。

| 站位坐标标识 (`position`) | 第一轮 (R1) 统计 | 第二轮 (R2) 统计 | 占比 (R2) | 规范性评估 |

## 七、客观数据暴露的技术瓶颈与事实结论

1. **落盘稳定性显著修复**：
   - Visual Prompt 落盘率由 R1 的 **0.6% 提升至 R2 的 97.6%**，证明资产提示词提取管线已具备工程化可用性。
2. **演出参数维度的单一性**：
   - 现存 49,843 步中，`show` 步骤仅包含 `characterId`、`expression` 与 `position`，**`shotType`（景别）、`scale`（缩放）与 `cameraEffect`（运镜）使用率为 0%**，印证了前置诊断报告中提出的“景别单一、无推拉运镜”的客观现状。
3. **立绘文件物理格式**：
   - 检查 `assets/images/characters/` 磁盘文件，现有图片为带有纯白底色的 24-bit RGB PNG 或 SVG 占位图，**32-bit RGBA 纯透明通道比例为 0%**，需要通过资产生成管线的 Alpha 自动抠图功能予以解决。
4. **长文本 Token 截断瓶颈**：
   - 在未通过场景及失败章节中，77.3% 的失败记录归因于长小说切片超过 1500 字导致的大模型输出 Token 溢出与 JSON 不完整。
